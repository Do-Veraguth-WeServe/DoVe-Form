# Direct question forms and ongoing blueprint discussion

User request 6364 (2026-11-08): answer one or multiple questions inside the form, choose an option or the last Own answer option, submit the whole form directly; never use the chat composer as a relay. Questions for work on an Element belong in its Blueprint.

Implementation: shared app-owned native radio/textarea form for ordinary choices and Blueprint questions. All controls are inert data, with explicit submission. Drafts and accepted status are scoped by account/conversation/message or blueprint revision in sessionStorage; pending lock is shared across rerenders in the current tab. Composer text is preserved. Admission failure keeps answers available for retry. New blueprint revisions have new question keys, and server rejects stale blueprint submissions and foreign conversations. Only the explicit build endpoint can build; question submission cannot.

A selected Element or explicit Blueprint answer uses the planner. Ordinary chat retains normal conversation, including unrelated questions during a build. When an existing Blueprint is present, the chat contract requires a validated blueprint metadata update for Element requirements/changes, with questions inside blueprint.questions rather than choices cards. Job completion saves this cumulative revision transactionally (base revision conflict check) and sends it through the live snapshot; no planning claim without persistence. The trusted server binds the revision to the existing target or completed build, never a model-supplied target ID. Fresh conversations cannot create a Blueprint through chat metadata without prior planning consent. No product code/state is changed automatically.

Question schema: legacy strings supported; new objects {text,options}. Up to 20 questions per form, 8 suggestions per question, 300-character question/custom answer and 160-character suggested option. Own answer is always appended by trusted UI. Questions may be grouped; no single-question-only UI. These explicit safety bounds replace the former five-question cap; more questions should be split into rounds. Form replies allow at most 16000 characters, ordinary composer messages remain 2000. Stored/imported text preserves the larger bound.

No migration of past chat answers or historic user products. Draft/sent UI status is tab-local, not cross-device submission deduplication. Existing request IDs still deduplicate transport retries. Model output remains probabilistic; schema validation and native rendering enforce bounded valid fields, but prose-only model questions cannot be magically converted into meaningful options.

Acceptance results recorded after tests.

Consistency guard: if a chat reply claims that a Blueprint was updated but supplies no structured revision, one bounded planner correction obtains the full plan; failure is surfaced instead of silently treating the prose claim as persisted. Ordinary unrelated discussion is not rerouted. This claim check is a bounded recovery heuristic, not a general intent classifier. A provider variant omitting only the reply XML wrapper is normalized while preserving every field/length/readiness check.
